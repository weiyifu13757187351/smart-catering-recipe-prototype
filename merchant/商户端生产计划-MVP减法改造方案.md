## 0. 结论速览

**一句话形态**：生产计划 = 排餐计划里「含设备加工的菜」的**当日执行清单**；每道菜只有两个动作 —— 开始生产（**在这一步决定设备与时间**）、生产完成。

| 类别 | 内容 |
| --- | --- |
| **保留** | 按日期查看（默认今天）、组织 / 档口切换、组织层档口总览、按餐次分段的当日任务清单、餐次 / 状态筛选、状态流转（未开始 / 生产中 / 生产完成）、撤销开工（当天） |
| **删除** | 设备时间轴视图、`scheduleAll` 倒推排程、灰字建议值、一键铺满、排期冲突 / 超时检测、计划加工时间列与行内输入、待排统计、「调整」抽屉（改设备 / 改时间 / 改锅数）、**任务详情抽屉**、设备筛选、开工定格、来源变更 / 已调整标记 |
| **新增** | 「开始生产」抽屉里确定 **生产设备 + 开工时间**；任务行只读展示**生产设备 / 加工时间**（开工后才有值） |
| **代码净减** | JS **−318 / 763 行（≈42%）**，CSS −57 / 220 行，PRD 第 5 章重写 |

**核心逻辑变化一句话**：`计划加工时间` 从「**开工前必须预排的排程输入**」变成「**开工时记录的现场事实**」。这一条变化把整套排程算法（倒推、建议值、冲突检测、时间轴）连根拔掉。

## 1. 现状盘点

### 1.1 生产计划页面现状（改造前）

`merchant-production-plan-v1.js` 当前由 6 块组成：

| 区块 | 代码位置 | 内容 |
| --- | --- | --- |
| 任务派生 | L41–142 | `tasksOf()` 从排餐读菜，派生 `output / inputTotal / potCount / mainDevice / plannedStart` 等 20 个字段；`opsOf / totalSec / durText / loadText` |
| 排程 | L144–236 | `listOrder / processOrder / scheduleAll`：按开餐时间**倒推**算建议时间 → 再检测**冲突 / 超时** |
| 状态流转 | L238–258 | `startBlock()`（没填时间不许开工）、`setStatus()`、`setOverride()` |
| 页面 | L262–526 | 档口总览 / 任务表（**11 列**）/ **设备时间轴**（泳道 = 设备，块 = 任务占用，74 行） |
| 交互 | L528–596 | 时间输入行内改、灰字建议值点击采用、一键铺满、开工硬校验 |
| 抽屉 | L598–755 | 「调整」（108 行，可改设备 / 时间 + 用料表 + 步骤表）、开工确认、撤销开工、完成确认 |

**统计卡 6 格**：当日任务 / 未开始 / 生产中 / 生产完成 / **待排** / **排期冲突**。
**筛选 3 项**：餐次 / **设备** / 状态。

### 1.2 最新排餐计划（V4）能提供什么

`merchant-meal-plan-v1.js` 的 V4 数据模型（`plans()[0]`，localStorage 键 `mp:plan:v4:{档口}:{周起始日}`）：

```js
{ id, start, activeDays,
  schedule: { [dayIndex]: { [餐次]: [菜谱ID, ...] } },   // 排什么菜
  perMeal:  { "d|m": { gram, memo, src } },              // 人均用餐量（克/人），档口配置为默认
  pots:     { "d|m|菜谱ID": 锅数 },                       // ★ 锅数是排餐侧的输入
  adjustments, updated }
```

| 生产计划要的东西 | 排餐计划侧的来源 | 口径 |
| --- | --- | --- |
| 今天要加工的菜 | `plan.schedule[dayIndex][餐次]` | 过滤 `hasDevice === true`，纯人工菜不进生产计划 |
| 锅数 | `MP.potsOf(plan, di, meal, id)` | **排餐侧输入**，生产计划只读（V3 起不再在生产计划里改） |
| 入锅投料总量 | `MP.inputTotalKg(...)` = `一锅基准投料 × 锅数` | 派生 |
| 出品量 | `MP.outputKg(...)` = `投料总量 × 出餐成品系数` | 派生 |
| 主加工设备 | `MP.mainStep(recipe).device` | 菜谱主加工步骤的设备（型号级） |
| 设备集合 / 容量 | `MP.effDevices(recipe, override)` / `MP.deviceCapacity(d)` | 4 个设备型号：智谷 A8 12kg、智谷 ZG-T30 30kg、优特 UT-C16 15kg、优特 UT-P40 14kg |
| 餐次与开餐时间 | `MP.meals()`（档口经营范围）/ `MP.OPEN_TIME`（档口另有 `meals[].start/end`） | 档口级 |
| 用料清单 | `MP.bomUsageOf(plan, di, meal, id)` | 派生 |
| 加工步骤 | `recipe.steps[]`（`stepName / device / seconds / isMain`） | 主数据 |

**关键结论**：新生产计划需要的**全部数据排餐侧都已具备**，不需要排餐侧做任何改动即可支撑本次减法。

### 1.3 为什么要减：现有复杂度全部来自"排程"

PRD 变更记录 19–30 条（`商户端计划管理PRD.md` L51–139）里，**10 条有 8 条是为排程打补丁**：倒推方向修正、任务内部连续性、已填时间先占位、假冲突、浮点尘埃导致 `16:60`、时间轴横轴自适应、窄块标签外挂、冲突计数筛选口径、`<input type="time">` 不支持 placeholder……每一条单独看都对，合起来是一套**没有人要求过的排程引擎**。

真正的业务场景是：**师傅站在灶前，看今天要做什么，点火，做完点一下。** 设备和时间是**那一刻**的事实，不是提前算出来的计划。

### 2.3 状态机（不变，但准入条件变了）

```
未开始 ──[开始生产：选设备 + 定开工时间]──▶ 生产中 ──[生产完成]──▶ 生产完成
   ▲                                          │
   └─────────[撤销开工（仅当天，清空设备与时间）]┘
```

| 状态 | 进入方式 | 可执行操作 |
| --- | --- | --- |
| 未开始 | 排餐保存后自动派生 | **开始生产**（无任何前置校验 —— 取消「没填时间不许开工」） |
| 生产中 | 开工抽屉确认（**设备 + 开工时间**同时落库） | **完成**、**撤销开工**（限当天） |
| 生产完成 | 完成抽屉确认（记完成时间） | 无（只读） |

### 2.4 三个动作的抽屉

**「开始生产」抽屉**

| 字段 | 类型 | 默认值 | 说明 |
| --- | --- | --- | --- |
| 餐次 · 菜名 | 标题 | — | 副标题 |
| 生产设备 | **下拉，必选** | 菜谱主加工设备 | 选项 = `recipe.steps` 涉及的设备型号（去重）；**只有一个选项时不渲染下拉**；改选时容量提示与装载即时重算 |
| 开工时间 | `input[type=time]`，**必填** | **当前时刻** | 这是本次改造里"决定时间"的落点 |
| 出品量 / 入锅投料总量 / 锅数 / 装载 / 预计总时长 | 只读回显 | 排餐派生 | 给动手的人一份完整指令 |

底部：`取消` / `确认开始生产` → `startTask(t,{device,at})`。

**「生产完成」抽屉**

显示：设备 / 开工时间 / 锅数 → 确认后写 `finishedAt = 当前时刻`。

**「撤销开工」**：保留（当天可回退，回到未开始并**清空设备与时间**）。理由：误点火是高频现场情况，且实现成本几乎为零。
**注意**：不做成「只清时间」—— 否则会出现「没有设备却在生产中」这种产品上不可能出现的行。

> **手机端额外保留只读详情抽屉**：车间要用「本次要称多少料」的用料清单，且撤销开工的入口在手机端放在详情里。
> 桌面端不做（Q5 改判）。

### 2.5 派生规则（沿用，不改）

1. 数据源 = 排餐计划中 `hasDevice === true` 的菜；
2. 聚合键 = `日期 × 餐次 × 菜谱`，无「生成生产计划」按钮，实时派生；
3. 纯人工菜不进生产计划（周五晚餐全人工菜 → 生产计划 0 道，仍成立）；
4. 未开工的任务跟随排餐自动刷新（改锅数 → 投料量 / 出品量跟着变）；
5. 已开工的任务：**MVP 不做开工定格**，继续跟随排餐刷新（比现状更简单，与 V3「两边不联动、生产只读排餐口径」一致）。
6. 生产计划**不再回写排餐计划的任何字段**（V3 之后排餐侧已完全没有生产状态，本方案维持）。

## 4. 数据模型变更

| 项 | 改造前 | 改造后 |
| --- | --- | --- |
| localStorage 键 | `pp:task:v1:{档口\|org}` | `pp:task:**v2**:{档口\|org}`（**升版让旧数据自动失效**，避免旧 `plannedStart` 伪装成新结构） |

| 时间语义 | `plannedStart` = 计划开始（分钟数，排程输入） | `startedAt` / `finishedAt` = 现场事实（分钟数，开工 / 完成时写入） |
| 示例数据 | `DEMO_DONE` 用 `scheduleAll` 反算建议时间 | 直接写 `{ status:'producing', device:'优特 UT-C16', startedAt: 11*60+40 }` |

> 分钟数（`toMin` / `hm`）口径不变，继续复用排餐侧工具函数。

## 9. 影响与风险

| 风险 | 说明 | 处置 |
| --- | --- | --- |
| 失去"提前排产"能力 | 后厨无法在开工前看到"今天几点做什么"，也无法提前发现抢设备 | **这是本次有意的取舍**；如后续需要，建议以「设备占用提示」这种轻量形式重做，而不是恢复整套排程引擎 |

| 归档/追溯 | 只有开工与完成两个时间点，没有"计划 vs 实际"对比 | MVP 可接受；如需要，`startedAt` 已足够做"实际加工时长"统计 |
